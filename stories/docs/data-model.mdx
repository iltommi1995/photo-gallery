# Data Model

The core relationship: **Album → Chapter → Placement → Photo**. A `Placement`
is the join between a `Chapter` and a `Photo` — it's where the ordering and
mosaic size live, so the same `Photo` can appear in multiple albums/chapters
without duplicating the file.

## Field notes

- **`Album.status`**: `DRAFT` | `PUBLISHED`. Only `PUBLISHED` albums are
  reachable at `/places/[slug]`; draft albums 404 on the public site but are
  fully visible/editable in the admin panel.
- **`Album.coverPhotoId`**: a plain photo id, not a foreign key relation —
  set via the cover-photo picker on the album settings form
  (`src/components/admin/AlbumSettingsForm.tsx`).
- **`Placement.colSpan` / `Placement.rowSpan`**: a free width × height in
  cells on the fixed 12×12 grid (`src/lib/gallery/grid.ts`), chosen per photo
  in the admin canvas rather than picked from a fixed size preset.
- **`Placement.gridColumn` / `Placement.gridRow`**: optional, one-based
  grid coordinates chosen in the chapter editor. Existing placements keep
  automatic layout until positioned; saving coordinates preserves intentional
  gaps in the shared gallery renderer.
- **`Chapter.viewport`**: `WEB` (default) | `MOBILE_LANDSCAPE` |
  `MOBILE_PORTRAIT`. A chapter belongs to exactly one — so an album's
  _chapter structure itself_ (how many chapters, their labels, their
  order), not just each chapter's photo content, can differ per context.
  An album's `WEB` chapters are the only ones that exist until an admin
  opts in via the Web / Mobile horizontal / Mobile vertical switch in the
  admin editor; creating chapters under either mobile value builds a fully
  independent structure for that context. Two separate mobile values, not
  one shared "mobile" structure, because a layout authored for a wide
  landscape phone doesn't translate to a narrow portrait one (or back) —
  chapter counts and spans/positions chosen for one render as paper-thin,
  broken slivers (or an awkward split) in the other. Whether a context "has
  an override" is a derived fact (any chapters of that viewport exist for
  the album), not a stored flag — the admin editor's "Clone from Web"
  action (`POST /api/admin/albums/[id]/chapters/clone`) gives a mobile
  context an editable starting point instead of a blank canvas, since
  authoring N chapters from scratch is a lot more work than restructuring a
  copy. No `WEB` chapters for the album → the album has no chapters at all
  (the empty-album state). No chapters for a mobile context → that context
  falls back to rendering `WEB`'s chapters: `MOBILE_LANDSCAPE`'s fallback
  is still a real grid (this context sits inside the `gallery-wide` CSS
  breakpoint regardless of which chapters are fed in); `MOBILE_PORTRAIT`'s
  fallback is `WEB`'s _photos_ in the ordinary single-full-width-row
  flatten, not their spans/positions. `Placement` itself carries no
  viewport of its own — it inherits its parent chapter's. See
  `docs/ai/add-album-layout-variant.md` and `ChapterMosaic`'s `forceGrid`
  prop.
- **`Photo`** carries both the storage paths (`originalPath` — the untouched
  upload, kept for EXIF backfill — plus `thumbnailPath`/`mediumPath`/`fullPath`,
  the `sharp`-generated display variants) and all EXIF/manual metadata
  (camera, lens, aperture, shutter speed, ISO, `takenAt`, GPS, plus
  `isAnalog`/`filmStock` for scanned negatives that have no EXIF at all).
  `altText` is nullable in the schema but treated as required by the admin
  metadata form — see `src/lib/schemas/photo.ts`.

## `SiteSettings` — not part of the original spec

A single-row table (`id: "singleton"`) holding the home hero photo, site
title, and About Me title/body/photo. It isn't part of the Album/Chapter/
Placement/Photo structure above — it exists because the home hero and About
page both need admin-editable content to live _somewhere_, and the original
data-model listing this project started from didn't include one. See
`prisma/schema.prisma`'s comment on the model for the full reasoning, and
`src/lib/settings.ts` for how the single row is read/created safely under
concurrent first-requests (a real race condition hit during a production
build — see `CHANGELOG.md`).

## Migrations

`prisma/migrations/` — never hand-edit a generated migration's SQL. Schema
changes go through `pnpm db:migrate` (or the `schema-guardian` Claude Code
agent / `docs/ai/add-album-layout-variant.md` for layout-shape changes
specifically).
